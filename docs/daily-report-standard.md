# WONLY 网站日报记录规范

## 1. 日报目的

网站日报用于向管理层说明当天实际完成并可核验的工作、产生的业务价值及遗留事项。日报以 Codex 与项目负责人的对话为线索，但不是聊天记录摘要，也不是待办清单。

## 2. 记录原则

### 只记录实际工作

满足以下任一条件，才可写入“已完成”：

- 网站代码、配置、内容或数据已经修改，并已核验修改结果；
- 第三方平台中的设置已经保存或发布，并能在后台或公开页面核验；
- 已完成分析并交付明确产物，如表格、文档、页面清单或优化方案；
- 已完成部署、构建、测试、邮件发送等操作，并获得成功结果。

以下内容不计为实际完成：

- 用户提出的问题、设想或口头确认；
- 仅讨论方案，但未执行；
- “继续”“按顺序做”等过程指令；
- 重复沟通、登录等待、权限确认；
- 未验证的修改或仅声称已完成的操作；
- 计划以后开展的工作。

### 以结果为中心

同一项工作的多轮对话合并成一条成果，不逐句记录操作过程。每条应回答：

1. 做了什么；
2. 做到什么范围；
3. 对询盘、SEO、内容、部署或运营有什么价值；
4. 是否已经验证。

### 不夸大完成度

- 已保存并验证：写“完成、上线、发布、配置、验证”。
- 已修改但未发布：写“完成本地修改，待提交/部署”。
- 已形成方案但未执行：放入“待办”，不得写成“完成”。
- 因权限、资料或第三方状态受阻：写清阻塞原因及下一步责任人。

## 3. 信息来源优先级

按以下证据判断工作状态：

1. 公开网站、第三方平台或服务器上的实际结果；
2. 构建、测试、发送、部署等成功日志；
3. Git 提交和文件差异；
4. 已交付的文档、Excel、图片等产物；
5. 对话中的操作说明。

对话说明与实际结果冲突时，以可验证结果为准。

## 4. 日报分类

- 页面建设：页面新增、改版、组件、表单、交互、多语言页面。
- 内容与 SEO：TDK、页面文案、FAQ、文章、内链、结构化数据、站点结构。
- 询盘转化：表单、邮箱、WhatsApp、在线客服、CTA、线索收集流程。
- 部署与工程：GitHub Actions、构建、Artifact、服务器部署、域名、证书。
- 运营与分析：搜索分析、竞品研究、数据报表、外链及社媒执行成果。
- 验证与修复：测试、线上核验、问题定位与已完成修复。

## 5. 工作日志格式

`docs/worklog.md` 每项独占一行，格式固定为：

```text
YYYY-MM-DD | 分类:实际成果；范围/数量；业务价值或验证结果
```

示例：

```text
2026-08-12 | 询盘转化:发布 12 条英文 FAQ，覆盖 MOQ、OEM/ODM、交期和报价等高频问题；统一引导客户提交项目资料，由项目经理在 24 小时内跟进
2026-08-12 | Tawk 配置:创建公开分类「Sales & Project Enquiries」，12 条文章全部设为 Public 并绑定询盘邮箱及 WhatsApp；已验证公开文章可访问
2026-08-12 | 部署与工程:完成 GitHub Actions 构建配置，生成可下载的 dist.zip Artifact；工作流运行成功
```

## 6. 对话总结流程

每次形成日报时，按以下顺序处理当天对话：

1. 提取所有用户目标和执行动作；
2. 合并属于同一成果的连续对话；
3. 删除纯咨询、计划、重复指令和登录过程；
4. 根据工具结果、文件修改、平台状态及公开页面判断完成度；
5. 将已完成成果写入当天工作日志；
6. 将未完成事项单独列为待办，不混入已完成工作；
7. 检查数量、网址、邮箱、语言和状态等关键事实是否准确；
8. 日报发布前再次核验当天日志与实际结果一致。

## 7. 表述要求

- 使用业务可理解的中文，不罗列无意义的命令或技术过程；
- 写具体页面、平台、数量、语言和状态，避免“优化网站”等空泛表达；
- 一项成果一行，建议 40–120 字；
- 同一成果只出现一次，避免重复计算工作量；
- 不记录密码、令牌、服务器密钥及其他敏感信息；
- 邮箱、域名、电话等公开业务信息可以记录，但必须核对准确。

## 8. 发布规则

- 网站日报脚本每天读取 `docs/worklog.md` 中北京时间当天的记录；
- 本地日志修改只有提交并推送 GitHub 后，GitHub Actions 才能读取；
- 日报中应区分“本地完成”“已推送”“已部署/已公开”；
- 如当日没有可验证成果，应如实写“无新增已完成事项”，不得用讨论内容填充。
